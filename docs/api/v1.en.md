# o-sumo Public API v1

[日本語版](./v1.md)

o-sumo serves static JSON. The currently published endpoints are:

- `GET /api/v1/banzuke.json`
- `GET /api/v1/torikumi.json`
- `GET /api/v1/rikishi.json`
- `GET /api/v1/rikishi/{id}.json`
- `GET /api/v1/rikishi-matchups.json`
- `GET /api/v1/gyoji.json`
- `GET /api/v1/gyoji/{id}.json`
- `GET /api/v1/yobidashi.json`
- `GET /api/v1/yobidashi/{id}.json`

Example base URL: `https://osada.us`

## Common Rules

- Content type: `application/json; charset=utf-8`
- Refresh model: periodically updated by GitHub Actions. See `docs/api/policy.en.md`
- Encoding: UTF-8, including Japanese strings
- Date format: `isoDate` uses `YYYY-MM-DD`; `updatedAt` is a generation timestamp string

Common top-level fields for banzuke/torikumi endpoints:

- `bashoName`: for example `"七月場所"`
- `year`: for example `"令和八年"`
- `updatedAt`: last generation date in JST. For torikumi it equals `max(resultUpdatedAt, scheduleUpdatedAt)`
- `resultUpdatedAt`: results archive update date in JST (torikumi only)
- `scheduleUpdatedAt`: schedule archive update date in JST (torikumi only)
- `source`: provenance for the value. `banzuke.json.updatedAt` is inherited from `torikumi.json.resultUpdatedAt`

The July basho is final. Until the September banzuke is officially published, `banzuke.json` and `torikumi.json` both remain on July (`202607`) current data. `resultDays` and `scheduleDays` are 15-day archive fields of `torikumi.json` only; immutable July snapshots support monthly HTML routes. No month-specific JSON endpoint or new API schema is added.

### Timestamp ownership

Each timestamp field has a single owner. Generator, UI, Markdown, and CI all read the same field for the same purpose. CI asserts `updatedAt === max(resultUpdatedAt, scheduleUpdatedAt)` and `banzuke.updatedAt === torikumi.resultUpdatedAt`.

- Banzuke (`banzuke.json`): `updatedAt` is bound to results — equals `torikumi.json.resultUpdatedAt`. It does NOT advance on schedule-only updates
- Results (`torikumi.json.resultDays`, results hub/day): `resultUpdatedAt`
- Schedule (`torikumi.json.scheduleDays`, schedule hub/day): `scheduleUpdatedAt`
- Archives (`/202603/`, `/202605/`, `/202607/`): each snapshot's `BanzukeData.updatedAt` / `TorikumiData.updatedAt`
- Rikishi index / detail (`rikishi.json`, `rikishi/{id}.json`): each JSON's `updatedAt`. Detail takes precedence over the index when both exist
- Rikishi matchups (`rikishi-matchups.json`): `updatedAt` from the last all-profile refresh that passed ID resolution and cross-profile consistency checks
- Gyoji / yobidashi index / detail (`gyoji.json`, `gyoji/{id}.json`, `yobidashi.json`, `yobidashi/{id}.json`): each JSON's `retrievedAt`
- News articles (`news-feed-update.yml`): each article's `publishedAt`. The feed's own `updatedAt` is NOT shown in the UI

Static pages that do not carry timestamps (Archives index, Kimarite index, etc.) must not display unrelated timestamps.

## `GET /api/v1/banzuke.json`

Banzuke data.

### Response Shape

- `bashoName`: for example `"七月場所"`
- `year`: for example `"令和八年"`
- `updatedAt`: results-bound timestamp in JST. Same value as `torikumi.json.resultUpdatedAt`
- `makuuchi`: array of rank groups such as Yokozuna and Ozeki
- `juryo`: array of rank groups

Rank group object:

- `title`: rank title
- `east`: east-side rikishi array
- `west`: west-side rikishi array

Rikishi object:

- `id`: rikishi ID
- `name`: shikona
- `yomi`: reading
- `rank`: banzuke label
- `side`: `east` or `west`
- `wins` / `losses` / `draws`: record totals
- `results`: per-day marks using `win`, `loss`, `draw`, or `null`; `null` means unsettled or unknown and is excluded from `wins`, `losses`, and `draws` totals
- `profileUrl`: Kyokai profile URL
- `memo`: notes

### Response Example

```json
{
  "bashoName": "七月場所",
  "year": "令和八年",
  "updatedAt": "2026-07-26T18:44:23+09:00",
  "makuuchi": [
    {
      "title": "横綱",
      "east": [
        {
          "id": 3842,
          "name": "豊昇龍",
          "yomi": "ほうしょうりゅう",
          "rank": "横綱",
          "side": "east",
          "wins": 11,
          "losses": 4,
          "draws": 0,
          "results": ["win", "win", "win", "loss"],
          "profileUrl": "https://www.sumo.or.jp/ResultRikishiData/profile/3842/",
          "memo": ""
        }
      ],
      "west": [
        {
          "id": 4227,
          "name": "大の里",
          "yomi": "おおのさと",
          "rank": "横綱",
          "side": "west",
          "wins": 0,
          "losses": 4,
          "draws": 11,
          "results": ["loss", "loss", "loss", "loss"],
          "profileUrl": "https://www.sumo.or.jp/ResultRikishiData/profile/4227/",
          "memo": ""
        }
      ]
    }
  ]
}
```

## `GET /api/v1/torikumi.json`

Torikumi results and schedule data.

### Response Shape

- `bashoName`: for example `"七月場所"`
- `year`: for example `"令和八年"`
- `updatedAt`: the latest of results / schedule / banzuke generation dates in JST. Equals `max(resultUpdatedAt, scheduleUpdatedAt)`
- `today`: current-day data with `makuuchi` and `juryo`
- `tomorrow`: next-day schedule data with `makuuchi` and `juryo`
- `resultDays`: 15-day results archive
- `scheduleDays`: 15-day schedule archive
- `resultUpdatedAt`: last results archive update date
- `scheduleUpdatedAt`: last schedule archive update date

Division object such as `today.makuuchi`:

- `day`: tournament day number, `1-15`
- `dayName`: for example `"取組日 十四日目"`
- `dayHead`: for example `"初日： 令和8年5月10日(日)"`
- `division`: `"幕内"` or `"十両"`
- `matches`: match array

`matches[]`:

- `division`
- `boutNo`
- `eastYomi` / `westYomi`
- `eastName` / `westName`
- `eastProfileUrl` / `westProfileUrl`
- `eastRank` / `westRank`
- `eastEnglish` / `westEnglish`
- `kimarite`
- `winner`: `east` / `west` / `null`

Daily archive object in `resultDays[]` or `scheduleDays[]`:

- `day`, `isoDate`, `pathDate`, `label`, `dayHead`
- `status`: `published` or `pending`
- `statusMessage`: `"結果未更新"` for results, `"取組予定未更新"` for schedules, or `null` when published
- `data`: `{ makuuchi, juryo }`

### Handling `pending` Days

When a day is not published yet, `status = "pending"`.

Recommended client behavior:

1. Keep the day page and URL available.
2. Show `statusMessage` instead of treating the day as missing.
3. Do not treat empty `matches` arrays as an error.
4. Expect `statusMessage` to be `"結果未更新"` for results or `"取組予定未更新"` for schedules.
5. Expect `matches` to be empty arrays on pending days.

### Historical Response Example (May 2026, format only)

```json
{
  "bashoName": "五月場所",
  "year": "令和八年",
  "updatedAt": "2026-06-29T14:16:57+09:00",
  "resultUpdatedAt": "2026-05-25T09:59:34+09:00",
  "scheduleUpdatedAt": "2026-06-29T14:16:57+09:00",
  "resultDays": [
    {
      "day": 1,
      "isoDate": "2026-05-10",
      "pathDate": "20260510",
      "label": "初日",
      "dayHead": "初日： 令和8年5月10日(日)",
      "status": "pending",
      "statusMessage": "結果未更新",
      "data": {
        "makuuchi": {
          "day": 1,
          "dayName": "取組日 初日",
          "dayHead": "初日： 令和8年5月10日(日)",
          "division": "幕内",
          "matches": []
        },
        "juryo": {
          "day": 1,
          "dayName": "取組日 初日",
          "dayHead": "初日： 令和8年5月10日(日)",
          "division": "十両",
          "matches": []
        }
      }
    }
  ]
}
```

On actual `pending` days, the daily archive object keeps the same shape, but `status` becomes `pending`, `statusMessage` becomes `"結果未更新"` or `"取組予定未更新"`, and `matches` stays empty.

## `GET /api/v1/rikishi.json`

List of basic rikishi information.

### Response Shape

- `updatedAt`: last generation date in JST
- `rikishi`: array of rikishi

Rikishi basic info object:

- `id`: rikishi ID
- `name`: shikona
- `yomi`: reading
- `currentRank`: current banzuke
- `profileUrl`: Kyokai profile URL

### Response Example

```json
{
  "updatedAt": "2026-04-14",
  "rikishi": [
    {
      "id": 3842,
      "name": "豊昇龍",
      "yomi": "ほうしょうりゅう",
      "currentRank": "横綱",
      "profileUrl": "https://www.sumo.or.jp/ResultRikishiData/profile/3842/"
    }
  ]
}
```

## `GET /api/v1/rikishi/{id}.json`

Detailed profile for a specific rikishi ID. Use an `id` value from `rikishi.json`.

### Response Shape

- `id`: rikishi ID
- `name`: shikona
- `yomi`: reading
- `currentRank`: current banzuke rank
- `birthDate`: birth date text (empty string if unavailable)
- `height`: height in cm
- `weight`: weight in kg
- `shusshin`: hometown or profile-origin text
- `debut`: debut basho text
- `careerStats`: career totals object
  - `wins`: total wins
  - `losses`: total losses
  - `draws`: total absences
- `photoUrl`: profile image URL (typically `/images/rikishi/{id}.png`). o-sumo prefers a local image processed with MiniMax I2I Generation from a Japan Sumo Association profile photo, or an empty string if unavailable
- `sourceUrl`: Kyokai profile URL
- `updatedAt`: last generation date for the detail JSON in JST

### Response Example

```json
{
  "id": 3842,
  "name": "豊昇龍",
  "yomi": "ほうしょうりゅう",
  "currentRank": "横綱",
  "birthDate": "平成11年5月22日（26歳）",
  "height": 188,
  "weight": 148,
  "shusshin": "東大関",
  "debut": "平成三十年一月場所",
  "careerStats": {
    "wins": 0,
    "losses": 0,
    "draws": 0
  },
  "photoUrl": "/images/rikishi/3842.png",
  "sourceUrl": "https://www.sumo.or.jp/ResultRikishiData/profile/3842/",
  "updatedAt": "2026-04-27"
}
```

## `GET /api/v1/rikishi-matchups.json`

Career head-to-head records for the current makuuchi and juryo rikishi, generated from the basho/day bout history published on Japan Sumo Association profiles. Shikona before and after a name change resolve to the same official rikishi ID. Absences and days without a bout do not count as wins or losses.

### Response Shape

- `updatedAt`: ISO 8601 timestamp written after every target profile passes retrieval, ID resolution, and cross-profile consistency checks
- `matchups`: array of ID pairs with recorded bouts
  - `rikishi1Id` / `rikishi2Id`: official rikishi IDs, always with `rikishi1Id < rikishi2Id`
  - `rikishi1Wins` / `rikishi2Wins`: non-negative integer win totals for the corresponding IDs

Each ID pair is unique. If a valid selected pair is absent, the comparison UI displays `0-0`. If the JSON request fails or the payload has an invalid schema, reversed IDs, or duplicate pairs, the UI reports the matchup as unknown instead of guessing.

### Response Example (excerpt)

```json
{
  "updatedAt": "2026-08-17T17:24:24+09:00",
  "matchups": [
    {
      "rikishi1Id": 4230,
      "rikishi2Id": 4279,
      "rikishi1Wins": 1,
      "rikishi2Wins": 5
    }
  ]
}
```

The comparison UI renders this example as `1-5` or `5-1` according to column order. Values reflect the official profile history available at generation time.

## `GET /api/v1/gyoji.json` / `GET /api/v1/yobidashi.json`

Lists of active gyoji and yobidashi sourced from the official Japan Sumo Association website. The current snapshot contains 42 gyoji and 45 yobidashi and has no photo or image fields.

### Response Shape

- `retrievedAt`: UTC time when the official site was fetched
- `source`: official member-list URL
- `officials`: profile summary array
  - `id`: official numeric ID, unique within the profile kind
  - `name` / `yomi` / `realName`: name, reading, and legal name
  - `rank` / `rankCode`: official rank and machine-readable rank code
  - `affiliation`: heya affiliation
  - `sourceUrl`: official individual profile URL

## `GET /api/v1/gyoji/{id}.json` / `GET /api/v1/yobidashi/{id}.json`

Detailed profile for an official numeric ID. Use an `officials[].id` value from the matching list endpoint. Numeric IDs can overlap between gyoji and yobidashi, so IDs are not shared across profile kinds.

The detail response adds these fields to the list entry:

- `kind`: `gyoji` or `yobidashi`
- `birthDate`: birth date (`YYYY-MM-DD`)
- `birthplace`: birthplace
- `adoptedAt`: adoption date (`YYYY-MM`)
- `retrievedAt`: UTC time when the official site was fetched
- `nameHistory`: gyoji name history, included only when published by the official profile
