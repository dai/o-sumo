# マイ力士のログイン・クラウド同期 プロバイダ比較計画

## 目的

現在の `localStorage` ベースのマイ力士を維持しながら、任意ログイン後は端末をまたいで登録力士を同期できる構成を選定する。

## 現状確認

- `app/lib/my-rikishi.ts` が `o-sumo:my-rikishi:v1` に数値 ID 配列を保存する。
- `useMyRikishi()`、番付、取組、力士名鑑、比較画面がこのローカル状態を共有する。
- 最大登録数は20人。
- サイトは静的 Cloudflare Pages を中心に構成され、Pages Functions と KV の利用実績がある。
- 未ログイン利用をなくさない。ログインは任意とし、ログイン前の選択を失わせない。

## 設計方針

1. UI から認証サービスを直接参照するのではなく、`MyRikishiStore` 相当の読み書き境界を設ける。
2. `localStorage` を匿名用アダプター、選定プロバイダをログイン用アダプターにする。
3. 初回ログイン時はローカル配列とクラウド配列を union し、重複を除いて保存する。上限20人を超える場合は追加順を保ち、切り捨て前にユーザーへ通知する。
4. 力士 ID だけを保存し、四股名や番付などの変動データは保存しない。表示は既存の公開 JSON を正とする。
5. 将来の通知設定、表示順、メモ、場所単位の追跡を見据え、保存モデルは `user_id` と `rikishi_id` の組み合わせを中心にする。
6. ログアウト時はクラウド状態を消さず、端末上の匿名状態へ戻す。退会時の削除 API とデータエクスポート方針を最初から決める。

## プロバイダ候補

### A. Supabase Auth + Postgres（第一候補）

- Auth、JWT、Social Login、Magic Link、MFA と Postgres/RLS を一体で使える。
- `my_rikishi(user_id, rikishi_id, sort_order, created_at)` を RLS で本人だけ読み書きできる形にしやすい。
- 無料枠は Auth 5万 MAU、DB 500MB、無料プロジェクトは1週間非アクティブで停止。Pro は月25ドルから、という現行表示。
- 長所: 今回の「認証 + ユーザー別データ保存」に最も自然。将来の設定・履歴・通知購読を SQL で拡張しやすく、データ所有権と移行性も比較的明確。
- 短所: Cloudflare Pages とは別サービスになる。RLS、OAuth リダイレクト、メール送信、バックアップを設計・運用する必要がある。
- 適性: 個人向けサイトとして小さく始め、登録データが増えても同じ基盤で育てたい場合。

### B. Clerk + 保存 API（Cloudflare Pages Functions または Supabase）

- サインイン、プロフィール、ソーシャルログイン、セッション UI の導入が速い。
- 現行 Hobby は1アプリあたり5万 MRU、Pro は月20ドルからという表示。MRU と MAU は課金単位が違うため、利用実態を計測してから予算化する。
- 長所: 認証 UX とアカウント管理を最短で整えられる。認証を Clerk、データを別 DB に分離できる。
- 短所: マイ力士の保存先は別途必要。Clerk 固有のユーザー ID と JWT 検証を Pages Functions 側で扱うため、二つのサービス境界が増える。
- 適性: 将来、プロフィール、組織、課金、管理画面など認証周辺の機能を重視する場合。

### C. Auth0 + 保存 API

- B2C のソーシャルログイン、パスワードレス、パスキー、MFA、企業向け接続を広くカバーする。
- 現行の無料枠は2.5万 MAU。Essentials は月35ドルから、Professional は月240ドルからという表示で、上位機能は急に高額になりやすい。
- 長所: 認証の成熟度、監査、企業 SSO、将来の複数サービス統合に強い。
- 短所: 個人向けのマイ力士だけには機能・費用・運用が過剰。保存 API と DB は別に必要。
- 適性: 将来、法人利用、外部サービス連携、厳格な監査要件が明確にある場合。

### D. Firebase Authentication + Firestore

- Google 系との統合、匿名認証、Web とモバイルの共通 SDK が強い。
- Auth の課金はプランと認証方式に依存し、現行資料では Spark に一部プロバイダの1日あたり上限、Blaze に認証 MAU の無償枠が示されている。Firestore の読み書き課金も含めて見積もる必要がある。
- 長所: 匿名状態からアカウントへの移行、Google ログイン、将来のアプリ化を進めやすい。
- 短所: Cloudflare Pages の現在の構成に Firebase SDK と Firestore を追加することになる。Firestore のドキュメント設計・ルール・読み取り回数の管理が必要。
- 適性: Android/iOS アプリ展開や Google エコシステムを明確に重視する場合。

### E. Cloudflare Workers + D1（認証も自前または OAuth 連携）

- Pages Functions で認証コールバックと API を持ち、D1 にユーザー別データを保存する Cloudflare 内製構成。
- Workers Free/有料の現行枠があり、D1 は無料枠と従量課金がある。Pages Functions は Workers として課金される。
- 長所: 配信基盤と実行基盤が近く、データ配置・請求・ログをまとめやすい。SQL を所有でき、ベンダー依存を減らせる。
- 短所: パスワード、セッション、OAuth state、CSRF、メール確認、退会、アカウント連携を自前で安全に実装する必要がある。OAuth だけを使っても認証サービスの責任範囲は大きい。
- 適性: 認証を自社の中核機能として運用する覚悟があり、Cloudflare への統一を優先する場合。

## 推奨順位

1. **Supabase Auth + Postgres**: 認証と保存を一つにまとめられ、今回の機能規模と将来拡張のバランスが最もよい。
2. **Clerk + Cloudflare API + D1**: 認証 UI を最速で出したい場合の代替。保存 API の境界を先に設計する。
3. **Firebase**: モバイル展開が近い場合に順位を上げる。
4. **Auth0**: 企業 SSO や監査要件が出た場合に選ぶ。
5. **自前 Cloudflare**: コストではなく制御権を優先し、認証実装を長期運用できる場合だけ選ぶ。

## 段階導入案

### Phase 0: プロバイダ非依存の境界

- `MyRikishiStore` の型とローカル実装を追加。
- 既存 UI は `useMyRikishi()` のまま利用し、保存処理だけを差し替え可能にする。
- union、上限、順序、壊れた保存値、ログアウト時の挙動をテストする。

### Phase 1: 匿名利用とログインの併存

- ログイン導線は任意表示とし、未ログインでも現状どおり動かす。
- 認証成功時にローカル配列とクラウド配列をマージする。
- 競合は「追加は union、削除は明示操作のタイムスタンプで判定」まで拡張できるデータ形を採用する。初期版は単純 union でよい。
- 通信失敗時はローカルへフォールバックし、ユーザー操作を失わない。

### Phase 2: アカウント管理とデータ契約

- 退会時の削除、エクスポート、連携解除、メールアドレス変更を実装。
- 公開 JSON の力士 ID が消滅・変更された場合の表示を定義。
- API レート制限、監査ログ、障害時の再試行、プロバイダ障害時の読み取り専用動作を追加。

## 選定前に決める項目

- 最初のログイン方式: Google のみか、Magic Link を含めるか。
- メールアドレスを保存する必要があるか。不要ならソーシャル ID と内部ユーザー ID のみでよい。
- 同期対象をマイ力士だけに限定するか、テーマ・言語・表示順も同期するか。
- 退会・データ削除・エクスポートの期限と責任者。
- 想定 MAU、ログイン頻度、同期 API の最大リクエスト数。
- 日本国内のユーザーを主対象とする場合のリージョン、プライバシーポリシー、委託先表記。

## 検証項目

- 未ログインで既存の localStorage 利用が完全に維持される。
- ログイン後、同一ユーザーの別ブラウザ・別端末で同じ登録力士が再現される。
- ログイン前の登録が消えず、クラウド側とのマージが重複しない。
- オフライン、401、429、プロバイダ障害時にローカル状態を失わない。
- ログアウト、退会、再ログインで意図しない別ユーザーのデータが表示されない。
- RLS または API 認可により、他ユーザーの `rikishi_id` を読めない・書けない。
- 現行の `npm test`、`npm run typecheck`、`npm run build` と Cloudflare Preview のブラウザ確認が通る。
